# lightwell_crossbranch_per_cve_logback — cross-branch suppression is per CVE, not per advisory

Snapshot: `lightwell-osv` @ `ae0cbae` (2026-11-13, 288 advisories). Rule: `--rule scoped`.
Encodes `docs/README.md` §4.2, §6 and Use case B — **and records a defect in Use case B.**

## The defect

Because every Lightwell record uses an open or base-anchored `introduced`, a remediated build on a
*low* branch falls inside the interval of records for *higher* branches. Dataset-wide there are
**154 such cross-branch matches: 56 pure false positives and 98 genuine findings.**

Docs §4.2 prose compares *the CVE* and is correct. **Use case B restates the rule per advisory** —
applied at advisory granularity it suppresses all 154, including the 98 genuine ones, which are the
majority. The rule must be applied per upstream CVE.

## Why not woodstox

The woodstox triple has **zero** cross-branch matches: all three branches are `scoped` with disjoint
intervals (see `lightwell_branch_isolation_woodstox`). It cannot demonstrate this behaviour at all.
`logback-core` can, and does so with both outcomes on a single build.

## Data
Three `ch.qos.logback:logback-core` advisories, vendored verbatim:

|---|---|---|---|---|
| `RHLW-2026-07e5370d09e5a6f8` | 1.5.9 | `0` | `1.5.9.rhlw-00031` | CVE-2024-12798, CVE-2024-12801, CVE-2026-10532, CVE-2026-19880 |
| `RHLW-2026-666a4e7d1066f856` | 1.5.16 | `0` | `1.5.16.rhlw-00002` | CVE-2026-10532 |
| `RHLW-2026-730f8211b080b586` | 1.5.18 | `0` | `1.5.18.rhlw-00003` | **CVE-2026-1225** |

## Expected (component × advisory) — matches `expected.json`
| Component | Version | …07e5 | …666a | …730f |
|---|---|---|---|---|
| `logback-1.5.9` | `1.5.9` | affected | affected | affected |
| `logback-1.5.9-rhlw` | `1.5.9.rhlw-00031` | — | affected | affected |

The second row is the fixture. `1.5.9.rhlw-00031` is the remediated build of its own advisory
`…07e5`, so `…07e5` correctly drops out — and two higher-branch advisories still match it:

```
ch.qos.logback:logback-core @ 1.5.9.rhlw-00031   (own advisory …07e5, base 1.5.9)
  matched by …666a (base 1.5.16)
      CVE-2026-10532 ⊆ own CVE set   -> SUPPRESS (false positive)
  matched by …730f (base 1.5.18)
      adds CVE-2026-1225             -> KEEP (genuinely affected)
```

**One query, two returned advisories, opposite correct answers.** A per-advisory rule gives the
same answer to both and is therefore wrong whichever answer it gives.

Trustify returns both matches and does not implement the per-CVE suppression — that is the
consumer's step, and this scenario pins the input it must receive. The verdict map records what
Trustify returns; the suppression decision above is the oracle's reading of it, and is deliberately
not encoded as a verdict, because no `VerdictStatus` expresses "matched but suppressed".

Expectations are generated by `tools/check_ranges.py`'s `in_range` + `comparator`, not by Trustify.
