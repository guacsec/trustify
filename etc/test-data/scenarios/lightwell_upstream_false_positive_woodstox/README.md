# lightwell_upstream_false_positive_woodstox — an unscoped query reports a remediated build as affected

Snapshot: `lightwell-osv` @ `ae0cbae` (2026-11-13, 288 advisories). Rule: `--rule scoped`.
Encodes `docs/README.md` §6.1, §6.2.

This is the problem Lightwell exists to solve, shown as a side-by-side contradiction on one build.

A Red Hat remediated build keeps its upstream version number and adds an `rhlw` suffix:
`6.2.2.rhlw-00004` is `6.2.2` *with the fix for CVE-2022-40152 backported*. Upstream advisories know
nothing about that suffix. The upstream GHSA says woodstox is affected below `6.4.0`, and
`6.2.2.rhlw-00004 < 6.4.0`, so **every scanner that consults only upstream data reports the
remediated build as vulnerable.** The finding is real-looking, actionable-looking, and wrong.

## Data
- `advisories/RHLW-2026-36d9ed0bb47c794f.json` — vendored verbatim. Scoped
  `Red Hat Lightwell:Maven`, `introduced: 6.2.2`, `fixed: 6.2.2.rhlw-00004`.
- `osv/GHSA-3f7h-mf4q-vrm4.json` — **authored for this scenario, not a copy of any upstream
  record.** Plain `Maven` ecosystem, `aliases: [CVE-2022-40152]`, one open range `fixed: 6.4.0`.
  It models the unscoped view of the same vulnerability the Lightwell record remediates.
  Simplified to a single affected entry, and `versions[]` is deliberately omitted so that the
  interval alone decides the match (no exact Generic safety net — see plan §6.3).

Because the authored record carries a CVE alias, Trustify keys its verdicts under
`CVE-2022-40152`; the Lightwell record has no `aliases`, only `upstream`, so it keeps its own
`RHLW-…` identity. The two therefore appear as distinct verdicts on the same component, which is
what makes the contradiction visible.

## Expected (component × advisory) — matches `expected.json`
| Component | Version | RHLW-2026-36d9ed0bb47c794f (scoped) | CVE-2022-40152 (unscoped) |
|---|---|---|---|
| `woodstox-6.2.2` | `6.2.2` | affected | affected |
| `woodstox-6.2.2-rhlw` | `6.2.2.rhlw-00004` | — | **affected ← false positive** |
| `woodstox-6.4.0` | `6.4.0` | — | — |

- **6.2.2** — both agree: genuinely affected. Upgrade to `6.2.2.rhlw-00004`.
- **6.2.2.rhlw-00004** — the two sources **contradict each other**. The scoped record is right: the
  build is remediated. The unscoped record produces the false positive. Resolving it requires
  knowing that the `rhlw` suffix marks a backport — see `lightwell_suffix_detection`.
- **6.4.0** — above the upstream fix; both silent.

Expectations are generated by `tools/check_ranges.py`'s `in_range` + `comparator`, not by Trustify.
