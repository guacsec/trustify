# lightwell_coverage_gap_woodstox — an empty response is not a remediation

Snapshot: `lightwell-osv` @ `ae0cbae` (2026-11-13, 288 advisories). Rule: `--rule scoped`.
Encodes `docs/README.md` §4.2 — **and records a defect in it.**

## The defect

Docs §4.2 states "An empty response means not affected" and "Query a fixed build and above → no
advisory for that line → that line is remediated." Both claims fail *between* branches.

Woodstox `6.0.2` is genuinely vulnerable to `CVE-2022-40152` and returns **empty**: it sits above
the 5.0.3 branch's fix and below the 6.0.3 branch's `introduced`. No Lightwell record covers it,
because Lightwell publishes one record per *remediated build*, not per vulnerable range.

Dataset-wide there are **78 such uncovered inter-branch gaps** across the 49 multi-branch packages:

```
woodstox-core: (5.0.3.rhlw-00001 .. 6.0.3)   EMPTY, uncovered
woodstox-core: (6.0.3.rhlw-00001 .. 6.2.2)   EMPTY, uncovered
okio:          (1.6.0.rhlw-00001 .. 1.17.2)  EMPTY, uncovered
```

The correct consumer reading is **"empty ⇒ no Lightwell statement; fall through to upstream data"**,
never "safe".

## Data
All three woodstox advisories, vendored verbatim: `…dd8e` (base 5.0.3), `…403d` (base 6.0.3),
`…36d9` (base 6.2.2).

| `woodstox-6.0.3` | `6.0.3` | `…403d` affected | control: the advisories *are* loaded |

The first three rows are indistinguishable in the verdict map — all empty — yet two mean "unknown"
and one means "fixed". **That is the defect.** The control row exists so that an empty result
cannot be explained away by the fixtures having failed to ingest.

Trustify's `VerdictStatus` does separate `affected` / `fixed` / `not_affected` / absent, so the
distinction is representable; what is missing is any Lightwell input that would populate it for
`6.0.2`.

Expectations are generated by `tools/check_ranges.py`'s `in_range` + `comparator`, not by Trustify.
