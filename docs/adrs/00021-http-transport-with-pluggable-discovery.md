# 00021. HTTP transport with pluggable file discovery

Date: 2026-08-26

## Status

PROPOSED

## Context

Trustify's existing importers rely on two transport mechanisms to fetch external data:

* **Git** — clone a repository and walk the filesystem (used by OSV, CSAF, CVE, CWE, SBOM
  importers).
* **OCI registry** — pull artifacts from a container registry (used by the Quay importer).

Neither supports importing data served over plain HTTP. This is a gap because advisory and
vulnerability data providers increasingly publish content through HTTP-based content
repositories rather than git repositories or container registries.

### The HTTP file listing problem

HTTP provides no standard method to enumerate files at a URL. A client can fetch a known file
with `GET`, but cannot ask "what files exist here?" — unlike git (where the repo *is* the file
listing) or OCI (where the registry API provides a manifest).

Common approaches to HTTP file discovery each have significant drawbacks:

| Approach | Drawback |
|----------|----------|
| **HTML directory index** | Not standardized — different servers produce different HTML. No checksums. Requires fragile HTML scraping that breaks when the server template changes. |
| **WebDAV `PROPFIND`** | Standardized (RFC 4918), but requires server-side WebDAV support. Most content repositories do not enable it. The `OPTIONS` response from typical content servers returns only `Allow: GET, HEAD`. |
| **Manifest file** | Requires the server to publish a known file listing. Not a universal standard, but simple, reliable, and provides integrity metadata (checksums, sizes). |

The manifest approach is the most practical for real-world content repositories: it works over
plain HTTP, requires no special server capabilities beyond static file serving, and can include
integrity data that the other approaches lack.

### Pulp as a content distribution platform

[Pulp](https://pulpproject.org/) is an open-source platform for managing and distributing
content repositories. It is widely used across the Red Hat ecosystem and beyond for publishing
software artifacts, advisories, and security data.

Pulp file-content distributions configured to serve a publication expose a `PULP_MANIFEST` file
at their root — a simple CSV format with three fields per line:

```
filename,sha256,size
```

This format is:
* **Simple** — trivially parseable, no special libraries needed.
* **Reliable** — machine-generated by Pulp, not dependent on server HTML templates.
* **Integrity-aware** — includes SHA256 checksums for every file, enabling verification after
  download.
* **Content-agnostic** — the manifest lists files regardless of their format. The same
  mechanism serves OSV advisories, CSAF documents, SBOMs, or any other supported format.

Trustify's ingestor already supports auto-detection of file formats (`Format::Unknown`), so an
HTTP transport that fetches files listed in a Pulp manifest can import any supported content
type without format-specific logic in the transport layer.

## Decision

### HTTP transport with pluggable discovery

Introduce an HTTP-based transport with two clearly separated concerns:

1. **File discovery** — determining what files are available at a source URL. This is the part
   that varies between content platforms, so it is implemented as a pluggable strategy.
2. **File retrieval** — downloading files, verifying integrity, and passing them to the
   ingestor. This is shared across all discovery strategies.

```
HTTP Transport (shared)
├── Authentication ──────────── ADR-00020
├── File retrieval ──────────── HTTP GET with retries
├── Integrity verification ──── when metadata available (digest, size)
├── Format detection ────────── ingestor auto-detection
└── Discovery strategy ──────── pluggable
    ├── Pulp Manifest ────────── implemented
    └── (future strategies)
```

### Discovery strategy interface

Each discovery strategy is responsible for:

* **Enumerating files** at a given source URL, returning a list of file paths.
* **Providing integrity metadata** when available — digest (SHA256, MD5, etc.), size, or
  both. These fields are optional; not all strategies can provide them.

The shared retrieval layer verifies whatever integrity metadata the strategy provides:
if a checksum is present, it is verified after download; if a size is present, it is
checked; if neither is available, the file is fetched without verification. This allows
strategies with rich metadata (Pulp Manifest: SHA256 + size) and strategies with limited
metadata (WebDAV: size only, static file list: none) to coexist in the same transport.

### Pulp Manifest strategy (first implementation)

The Pulp Manifest strategy:

1. Fetches `{source_url}/PULP_MANIFEST`.
2. Parses the CSV to extract file paths, SHA256 checksums, and sizes.
3. Supports glob-style pattern filtering (`only_patterns`) to select a subset of files.
4. Returns the file list to the shared retrieval layer, which downloads each file, verifies
   its SHA256 checksum and size, and passes it to the ingestor.

#### Configuration example

```json
{
  "source": "https://packages.example.com/content/advisories/",
  "discovery": "pulp",
  "auth": {
    "type": "basic",
    "username": { "source": "env", "name": "IMPORTER_USERNAME" },
    "password": { "source": "env", "name": "IMPORTER_PASSWORD" }
  },
  "onlyPatterns": ["*.json"],
  "fetchRetries": 3
}
```

Authentication follows [ADR-00020](00020-importer-credential-resolution.md) — the HTTP
transport uses the shared auth model and credential source abstraction.

### Extensibility for future strategies

The pluggable discovery design allows adding new strategies without modifying the transport
core. Potential future strategies include:

| Strategy | Discovery mechanism | When to consider |
|----------|-------------------|------------------|
| **WebDAV** | `PROPFIND` (RFC 4918) | When the source server enables WebDAV — provides standardized directory listing with file size, timestamps, and ETags, but no checksums. Size verification applies; digest verification is not available. |
| **SHA256SUMS** | Standard checksum file | When the source publishes a `SHA256SUMS` file (common in Linux distribution mirrors). |
| **Static file list** | User-provided list of URLs | When the file set is small and known in advance — no server-side discovery needed. |

Adding a new strategy requires implementing the discovery interface. The shared retrieval
layer, authentication, integrity verification, and format detection remain unchanged.

### Existing dependencies for implementation

Two primitives from `walker-common` (already a Trustify dependency via `csaf-walker`) are
candidates for reuse rather than reimplementation:

* **`walker_common::fetcher::Fetcher`** — retry and rate-limit logic on top of reqwest.
  Covers exponential backoff and HTTP 429 handling. Does not support authentication; auth
  headers are applied at the reqwest `Client` level before passing to the fetcher.
* **`walker_common::retrieve::RetrievedDigest<D>`** — generic digest verification
  (`expected` vs `actual`) over any `digest::Digest` impl (SHA-256, SHA-512, MD5, etc.).
  Aligns with the flexible integrity model described in this ADR.

The CSAF-specific discovery logic (provider-metadata.json, ROLIE feeds, OpenPGP signatures)
is not applicable to the Pulp manifest use case and is not reused.

## Alternatives considered

### HTML directory index scraping

Parse the HTML auto-index page that some HTTP servers generate for directory listings.

**Why not chosen:** HTML directory listings are not standardized — each web server (Apache,
nginx, Caddy) produces different HTML. The format can change with server upgrades or
configuration changes. There are no checksums or integrity data. This approach is fragile and
unsuitable for production use.

### WebDAV as the primary strategy

Use WebDAV `PROPFIND` as the default file discovery mechanism.

**Why not chosen:** WebDAV requires server-side support that most content repositories do not
enable. Querying the target endpoints with `OPTIONS` typically returns `Allow: GET, HEAD` —
no WebDAV methods. Building on a capability that the target servers do not offer would make
the importer unusable in practice. WebDAV remains a valid future strategy for servers that
support it.

### One importer per format over HTTP

Create separate importers for each format served over HTTP (e.g., an "HTTP OSV importer",
an "HTTP CSAF importer").

**Why not chosen:** The transport mechanism (how to list and fetch files) is independent of
the content format. Duplicating transport logic per format violates separation of concerns and
creates maintenance burden. The ingestor already auto-detects formats, so the transport does
not need to know what it is fetching.

### Custom REST API integration

Build importers that call provider-specific REST APIs to fetch advisory or vulnerability data.

**Why not chosen:** There is no industry-standard REST API for distributing OSV, OpenVEX, or
NVD data. The only advisory format with a standardized distribution protocol is CSAF, which
defines both a directory-based and a ROLIE-based (RFC 8322) distribution mechanism — and
Trustify already supports this through its existing CSAF walker. For all other formats,
providers distribute data as static files (via git repos or HTTP content repositories), not
through standardized APIs. Building custom API integrations per provider would create
maintenance burden with no standards to rely on. The manifest-based HTTP transport covers the
common case — static files served over HTTP — without coupling to any provider's proprietary
API.

## Consequences

* A new HTTP transport is added to the importer module with a pluggable discovery strategy
  interface.
* The Pulp Manifest strategy is the first implementation, enabling import of any supported
  file format from Pulp-served content repositories.
* Authentication is delegated to the shared model defined in
  [ADR-00020](00020-importer-credential-resolution.md).
* Format detection is delegated to the ingestor's existing auto-detection — the transport
  is content-agnostic.
* File integrity is verified using whatever metadata the discovery strategy provides
  (digest, size, or both). Verification is best-effort — strategies that provide no
  integrity metadata result in unverified downloads.
* New discovery strategies (WebDAV, SHA256SUMS, etc.) can be added without modifying the
  transport core or existing strategies.
* The transport supports glob-style pattern filtering, allowing operators to select a subset
  of files from a repository.
